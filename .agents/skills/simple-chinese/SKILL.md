# 简明中文

本仓库的说明文本写给一个赶时间、只读一遍的读者。每句话读一遍就要读懂。

规则的结构参考 ASD-STE100 简化技术英语：一句一事、限长、一个东西一个名字、条件在前。英语语法层面的规则（冠词、时态、情态动词）不适用于中文，已去掉。本仓库公开文本的规矩并在第 4 节。

## 适用范围

| 用 | 不用 |
|---|---|
| commit 消息、PR 与 issue 文本、CHANGELOG、README、CONTRIBUTING、代码注释、安装器的提示输出 | 游戏内的译文本身。译文要忠实原文与真源，按 `AGENTS.md`「译名的真源在哪里」处理 |

## 步骤

1. 确认读者。玩家读 CHANGELOG 与 README，贡献者读 CONTRIBUTING 与 PR，读代码的人读注释与 commit。
2. 把每段分成「操作」或「说明」。操作告诉读者做什么，说明告诉读者是什么。两种不混在一段里。
3. 动笔前先定词。一个概念只选一个词，全文不换（见规则 1.1 与「定词」）。
4. 按下面的规则写。
5. 交付前跑「自检」。这一步必做。
6. 不改「不动的内容」里列出的东西。

审查别人的文本时，每处问题按这个格式报：规则编号、原文、改写。只引用本文件里存在的编号。

## 规则

### 1 词

| 编号 | 规则 |
|---|---|
| 1.1 | 一个东西一个名字。全文用同一个词指同一个东西，不为了避免重复换说法。 |
| 1.2 | 游戏里的东西用游戏内显示的中文名（物品、模组、界面），不自己改写。 |
| 1.3 | 术语第一次出现写全称，后面可以用简称。 |
| 1.4 | 不用口语。白搭、翻车、炸了、病根、路子、直接敲，写成不生效、事故、崩溃、根因、途径、执行。 |
| 1.5 | 不用空话词，见「空话替换表」。删掉后意思不变的词就删掉。 |
| 1.6 | 能数出来的写数字，不写「大量」「若干」「一系列」。能由脚本算出来的数字不手写进文档，手写的数字会过时。 |
| 1.7 | 动作用动词表达。写「校验文件」，不写「对文件进行校验」。 |

### 2 句子

| 编号 | 规则 |
|---|---|
| 2.1 | 一句只说一件事。 |
| 2.2 | 操作句不超过 30 字，说明句不超过 40 字。计数方法见本节末尾。 |
| 2.3 | 条件放在动作前面。写「如果构建失败，先读日志」，不写「先读日志，如果构建失败」。 |
| 2.4 | 说清谁做了什么。写「安装器跳过这个文件」，不写「该文件会被跳过」。 |
| 2.5 | 不用分号。分号两边写成两句。 |
| 2.6 | 不省成电报体。主语、宾语和「的」该有就有。 |
| 2.7 | 三件以上并列的事用列表，不挤在一句里。 |

计数方法：每个汉字与中文标点算 1。一段连续的英文、数字、代码、路径或标识符整体算 1。所以 `scripts/compliance/protect.py --update` 只算 1，长路径不会把句子撑爆。

### 3 段落与结构

| 编号 | 规则 |
|---|---|
| 3.1 | 一段一个主题，最多 5 句。 |
| 3.2 | 先写结论，再写依据。 |
| 3.3 | 标题写陈述句。写「服务端必须单独装的三类文本」，不写「为什么服务端也要单独装」。 |
| 3.4 | 需要横向对比时用表格。同类条目并进一张表，不拆成多张单行表。 |
| 3.5 | 只写现在是什么、怎么用、动了会坏什么。不写这段文字以前长什么样。 |

### 4 公开文本

本仓库的 commit、PR、issue、CHANGELOG、README 与注释都公开可见，而且永久可搜。

| 编号 | 规则 |
|---|---|
| 4.1 | 只写事，不写人。不写谁提的、谁拍板、私下怎么沟通的。理由落在技术依据上。 |
| 4.2 | 不写本地环境：本地、本机路径、`/Users/`、机器名。 |
| 4.3 | 不写历史经过：「原先……现在改成……」「曾经」「一度」。历史在 git 里。如果那段历史仍在约束读者，就写成规矩（「别改回直写」），不写成故事。 |
| 4.4 | 不写自我检讨。只写这次改了什么、依据是什么。 |
| 4.5 | 改自己的错时，不点名牵涉到的人，用中性措辞。 |
| 4.6 | 不评价其他汉化项目，不记录外部传闻。 |
| 4.7 | 致谢只写名字和链接，不替别人写他做了什么。 |

### 5 各类文本的写法

| 文本 | 写法 |
|---|---|
| commit 标题 | 一行，「类型: 动作 + 对象」，关联 issue 时末尾写 `(#N)`。格式见 `AGENTS.md`「Git 与 PR」。 |
| commit 正文 | 默认不写。只在改动看不出根因、代码注释里又放不下时写，三到五行。 |
| PR 正文 | 见 [`create-pr`](../create-pr/SKILL.md)。 |
| CHANGELOG | 见 [`write-changelog`](../write-changelog/SKILL.md)。 |
| README | 只写读者能据此做决定的内容：装什么、怎么装、支持哪些版本、翻了多少、出问题去哪提。原理写进代码注释。 |
| 代码注释 | 一句话：「X 会导致 Y，所以不要改 Z」。不加小标题，不写历史，不用修辞。注释比它说明的代码还长，就是写多了。 |
| issue 回复 | 先结论，再依据，最后写读者能做的事。 |
| 安装器提示 | 发生了什么，原因（已知时），读者该怎么做。不道歉，不卖萌。 |

## 定词

下面每组词在本仓库里容易轮换。每组只选一个，一篇文本里不换。

- 校验、核对、检查、验证
- 配置、设置、选项
- 删除、移除、剔除
- 报错、错误、异常、失败。报错指出现的提示，失败指操作没成功。
- 运行、执行、跑
- 显示、展示、呈现
- 译名、译文、翻译。译名指名字，译文指句子与段落。

## 空话替换表

| 写了 | 改成 |
|---|---|
| 值得注意的是、需要指出的是、重要的是 | 删掉，直接写事实 |
| 进行修改、进行校验 | 修改、校验 |
| 对 X 进行了 Y | Y 了 X |
| 实现了对 X 的支持 | 支持 X |
| 有效地、显著地、极大地、全面地 | 删掉，或给出数字 |
| 无缝、一站式、强大的、完善的、健壮的 | 删掉，或写出可测量的性质 |
| 旨在、致力于、用于实现 | 删掉，直接写它做什么 |
| 基于……的考虑、出于……的目的 | 因为、为了 |
| 在……的情况下 | 如果 |
| 一定程度上、某种意义上、相对而言 | 删掉，或给出范围 |
| 等等、之类、诸如此类 | 列全，或写「另外 N 项」 |
| 简单地、轻松地、只需 | 删掉 |
| 深入探讨、剖析 | 查看、分析 |
| 赋能、抓手、闭环、打通、链路 | 写具体动作 |
| 不仅……而且……、不是……而是……（修辞对仗） | 只写事实那一半 |
| 综上所述、总而言之、总的来说 | 删掉 |
| 我们可以看到、可以发现、让我们 | 删掉 |

## 不动的内容

以下内容原样保留，不套用本规范：

- 代码块、行内代码、标识符、命令、参数、文件路径
- 报错原文与日志行
- 游戏内显示的物品名、模组名、界面文字
- 配置键、语言键、版本号

## 自检

交付前对草稿跑完这五项。发现问题就改，改完再交付。

1. 数最长的三句。操作句超过 30 字、说明句超过 40 字，就拆开。
2. 搜「；」「进行」「值得注意」「旨在」「等等」「之类」「原先」「曾经」，每一处都按规则改掉。
3. 搜每个「如果」「当」「若」。条件要在动作前面。
4. 搜第 3 步没选中的同义词，换成选中的那个。
5. 公开文本跑禁词检查，命中就改写。「实例」只在指玩家的游戏实例时保留。

   ```bash
   git log -1 --format=%B | grep -nE "用户|报告人|反馈者|提议者|迎合|口味|他说|私下|本地|实例|/Users/|机器"
   grep -nE "用户|报告人|反馈者|提议者|迎合|口味|他说|私下|本地|实例|/Users/|机器" <PR 或 issue 正文文件>
   ```

## 例子

改写前：

> 值得注意的是，本次更新对潘马斯农场2的翻译进行了全面的优化，有效地解决了物品名称翻译不准确等一系列问题，从而显著提升了玩家的游戏体验。

改写后：

> 潘马斯农场2 的 Stock 改译为「底汤」。原译「库存」把汤底译成了存货。

改动：

- 删掉「值得注意的是」「全面的」「有效地」「显著提升」。
- 「进行了优化」改成具体动作。
- 「等一系列问题」改成那一个具体问题。
- 一句拆成两句，每句一件事。
