# 写更新日志

`CHANGELOG.md` 写给玩家。玩家只关心修没修、改了什么、自己那一版受不受影响、装完要不要做别的。

## 第一步：确定版本节

动笔前先确认写进哪一节。这一步必做。

1. 查最近的 release：

   ```bash
   curl -s "https://api.github.com/repos/chiba233/atm10-zh-cn/releases?per_page=5" \
     | python3 -c "import json,sys; [print(r['tag_name'], r['prerelease']) for r in json.load(sys.stdin)]"
   ```

2. 取 `prerelease` 为 `False` 的最新一个，例如 `vr26`。beta 是预发布，不算发布。
3. 新内容写进下一个版本号的节，例如 `## R27`。如果顶节已经是这一节，就接着写。如果顶节是已发布的版本，就在最上面开新节。

不要用 `git tag` 或 CHANGELOG 顶节的标题来判断。顶节的那一版可能已经发布了。

### 已发布的节不改

- 已发布版本的节，一个字都不加。
- 唯一的例外是勘误：节里写错的事实可以改正。
- 漏记的内容不补。一个提交属于哪一版，用 `git log --oneline <tag>..HEAD` 判断。列表里的提交进新节，其余的属于已发布的版本。

## 第二步：写条目

写之前先问：玩家拿这句话能做什么决定？答不上来就删。

写这些：

- 修没修，改了什么
- 哪些整合包版本受影响
- 装完要不要做别的，例如重装、服主改配置
- 有什么代价

不写这些：根因、机制、字节码、扫描口径、脚本改法、闸的设计、报错串、mod id、类名。它们写进 commit 正文和代码注释。玩家看得见的后果可以写，例如「游戏起不来」。

## 格式

- 节名：`## R<序号>`。
- 节内按主题分 `###`，例如 `### 支持 All the Mods 10 **8.2**`、`### 其他修复`。
- 每个 `###` 下一张表，同类条目并成行。不给每条单开一张单行表。
- 表头固定：`| 哪里 | 之前 | 现在 |`。
- 「哪里」写玩家认得的位置：模组中文名加粗，再写界面或物品。受影响的整合包版本写在括号里。
- 名字用游戏内显示的中文，与 `AGENTS.md`「译名的真源在哪里」一致。
- 条目不写成散文段落。
- 玩家可见的改动，与它的更新日志放在同一个 PR 里。

例子（R27 的一行）：

```markdown
| 哪里 | 之前 | 现在 |
|---|---|---|
| **潘马斯农场2 - 食物核心**的 Stock | 物品名写作「库存」——这里的 Stock 是熬汤用的汤底，不是存货 | 「底汤」，与 MC百科收录的名称一致 |
```

## 致谢

- 修的是 issue 反馈的问题时，在本版本节末尾加 `### 致谢`。
- 格式：`感谢 **[名字](链接)** 的反馈：[#N](issue 链接)。` 多个 issue 用「、」分隔。
- 名字与链接照抄 issue 作者的主页，不猜。
- 只写名字和链接，不写他发现了什么。
- README 的致谢名单只放长期测试者。一次性的反馈者只进 CHANGELOG。

## 自检

1. 节名对应「最新正式 release 的下一版」。
2. 每一行都能回答「玩家拿它能做什么决定」。
3. 搜「根因」「字节码」「类名」与报错串。找到的删掉，或挪进 commit 正文。
4. 修了 issue 的，致谢已加。
5. 按 [`simple-chinese`](../simple-chinese/SKILL.md) 的自检再跑一遍。
